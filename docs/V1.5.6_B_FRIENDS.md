# TRIALUM 1.5.6-B — Friends / invites (private beta contract)

**Implementation scope:** opt-in pseudonymous online identity and durable friend consent. The 1.5.5 offline game and legacy WebRTC direct pairing remain available independently. This is a staged source update, not final 1.5.6 release or evidence of two-phone success.

## User flow
1. In **Friends**, consent to create a pseudonymous nickname (1–32 chars). No phone, email, Google account or contacts permission. Credentials are generated by the server, not invented by client.
2. [Create invite] produces a cryptographically random 32-byte, 15-minute one-use code, and invokes the Android Sharesheet to share an **HTTPS link with a fragment** `https://configured-host/invite#TOKEN`. The fragment is not sent in the HTTP request. `/invite` serves a locally rendered, no-third-party-resources landing page with an explicit [Open TRIALUM] link and manual code fallback.
3. Receiver opens TRIALUM `trialum://invite/TOKEN`; Android code validates the scheme/host and exact token length. Preview shows inviter nickname before [Accept]; NO auto-accept when opening a link. Only receiver can accept. One code cannot pair a third user afterward.
4. Friend list is stored server-side, with unilateral removal and block. The inviter sees a new friend after refreshing; push/presence comes later.
5. A friendship alone does not create shared playground membership or permit pet transfer. No pet data, XP, currency or chat is sent in 1.5.6-B.

## Security details
- Credential per installation is a 32-byte server-issued Bearer token, SHA-256 only in PostgreSQL. Android uses Keystore AES-GCM for its local token. Never copy/store this token in JSON game state, backup, cloud save, Git, URL or push payload.
- Invites are SHA-256 at rest, single-use under PostgreSQL transaction row lock, default 15-minute TTL, short rate limits; accept vs block serialized using transaction-level advisory locks. No self-invite.
- New SQL app role can read/write only identity/invite/friendship/blocks tables; it cannot read pet or playground tables. Separate health role retains SELECT 1 only.
- Endpoints intentionally disabled until `TRIALUM_SOCIAL_ENABLED=true`. Android builds only enable UI network mode if a designated **HTTPS** origin is configured at build time (`-PtrialumSocialApiUrl=https://host`), otherwise show a clear offline status. No arbitrary runtime server URL entry.
- Origin restriction defaults to `https://appassets.androidplatform.net`; backend accepts authorized non-browser requests without Origin for CLI tests. TLS/public edge auth/rate-limit security review REQUIRED before public Funnel.
- The advertised HTTPS site is a click-through landing page, NOT Android verified App Links. Proper App Links require owned domain verification via `.well-known/assetlinks.json` in a later production phase.
- Native Google Nearby Connections discovery is NOT shipped here: no unconsented Bluetooth/Wi-Fi/location permissions; add only after Android permission + physical-device QA and the user explicitly opts into nearby mode.
- Old P2P manual mode remains under an advanced expander, marked **unauthenticated**; never treat its profile as a server friend or trust its XP/visits.

## API operations (v1/social)
- `POST register` — optional nickname -> ephemeral response with identity + one-time credential
- `GET me` — owner identity (Bearer)
- `POST invites` — creates one-use invite, revokes previous pending inviter tokens
- `POST invites/preview` — token -> limited inviter nickname and expiry after authenticated request
- `POST invites/accept` — authenticated consent, single-use, atomic
- `GET friends` — list accepted friends only
- `DELETE friends/:id` — remove accepted friend
- `POST friends/:id/block` — block and remove
- `DELETE account` — delete stage-B social account; shared contribution-ledger deletion policy needed before 1.5.6-D
- `GET /invite` — HTML landing with no tracking, token only in hash fragment
