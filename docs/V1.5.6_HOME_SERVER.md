# TRIALUM Social Server — Ubuntu NAS-safe installation plan

**Status:** foundation build only; health/meta API, no real social login, friends, shared world or push yet. Never expose it publicly as a finished game service.

## Existing environment and invariants
User has an Ubuntu server also used as a home NAS, router-hosted WireGuard VPN, and a No-IP DDNS for private Webmin access. Do not change Webmin, router configuration, WireGuard, NAS services, storage mounts, firewall, or other workloads in automated scripts. Do not publish the Webmin hostname or credentials in application config or logs. Confirm Webmin is reachable ONLY through VPN; remote access via a DDNS name by itself is not proof of restriction.

## Network stages
1. **Private smoke test first**: Docker binds social API to loopback only at 127.0.0.1:8787, DB container on an internal Docker network with NO published 5432.
2. For restricted external beta ONLY after API authentication and invite abuse controls pass: install Tailscale on Ubuntu as a separate agent; existing router WireGuard continues unchanged. Tailscale **Funnel is public** even though the device is in a private tailnet; it does not authenticate users. A public Funnel requires real API authentication and rate limiting, plus abuse/security review. Enable MagicDNS/HTTPS and Funnel authorization in Tailscale admin, then `sudo tailscale funnel --bg 8787` (verify actual CLI installed and TLS URL returned), and inspect `tailscale funnel status`. Tailscale limits bandwidth; paid/commercial usage should be reviewed against current plan terms.
3. For production after acquiring a domain, move DB + API onto separate VPS/cloud network, use managed DNS and HTTPS/WSS, WAF/rate protection, monitored backups. Never rely on a consumer home/NAS server for a large public audience.

Docs: https://tailscale.com/docs/features/tailscale-funnel / https://tailscale.com/docs/reference/tailscale-cli/funnel

## Preparation — as a non-root admin over WireGuard
Do NOT run before verifying enough free disk/RAM and unaffected NAS workloads:

```bash
uname -a
lsb_release -a
df -h
free -h
docker --version
docker compose version
sudo ss -tulpn | grep -E ':(8787|5432|10000|80|443)\\b' || true
```

A port may already serve something important; if 8787 is used, choose a different *loopback-only* host port in `server/.env`. Never forward it on the router.

## First startup — private/localhost only
From a GitHub Desktop-synced copy of the repository on the server:

```bash
cd Trialum/server
cp .env.example .env
# edit .env and set a unique strong PG password; do not commit .env
nano .env
docker compose config
docker compose up -d --build
docker compose ps
curl --fail --silent http://127.0.0.1:8787/healthz
curl --fail --silent http://127.0.0.1:8787/v1/meta
```

The API is intentionally only a readiness/metadata scaffold. It responds to no invite, chat, payments or playground mutation endpoints. Do not enable Funnel just to expose this pre-authentication scaffold as a supposed public server.

## Validation and recovery
- `docker compose logs --tail=80 trialum-api` (no secrets or personal payloads should be logged)
- `docker compose stop` (non-destructive)
- `docker compose down` stops containers; **do not use -v**, as it deletes DB volumes.
- `docker compose pull && docker compose up -d --build` only after a reviewed release.
- Backups: encrypted Postgres `pg_dump` to an explicitly selected protected directory *outside the container*; verify a restoration into an isolated test database. No mounting whole NAS share and no automatic upload of user backups to external providers.
- Server starts with all social mutation endpoints disabled. Never publish localhost port through reverse proxy before auth, invite verification, schema migrations and threat model review are implemented and tested.
- Check firewall rules, Docker network isolation, Webmin accessibility without VPN from outside (using a separate phone on mobile data), dependency vulnerabilities, image signatures, patch cycle and resource limits.

## Future configuration interfaces (not active yet)
API base URL injected by an explicit build config; DO NOT hardcode historical No-IP hostname. WSS shares HTTPS origin. Remote credentials provisioned per device and never included in share links. FCM service account secret only in environment/secret manager, never Git, never image. Local save snapshots remain on device except explicitly opted-in backup. Remember that a tunnel provider processes network metadata.
