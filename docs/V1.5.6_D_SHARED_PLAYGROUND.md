# TRIALUM 1.5.6-D — Private shared playground and friend visits

**Status: development beta, NOT public rollout.** Branch `feature/trialum-1.5.6-d-shared-playground`. Does not change the private Ubuntu host, NAS, Webmin or router. Social feature remains opt-in and OFF by default.

## Shipped in source

- Distinct invitation-only playground rooms, up to 8 people; no implicit merging of the owner's friends or the guest's other friends.
- Owners create rooms and explicitly invite existing friends with 15-minute one-use codes bound to a specific recipient. Guests must accept. Members may leave. Owner can revoke membership, but cannot leave until future transfer/retirement flow is designed.
- Shared playground has its own server-owned starter toys, tier, and **earned effort wallet**, completely separate from offline local save, XP and local credits. Guests can enter the room even if their solo playground is still locked; no solo unlock is granted.
- Authenticated, recipient-approved 10-minute pet visit request to friend's home or a room that both already belong to. Pending/accepted visits expire or can be returned; no real pet record is deleted or moved. `pet_ref` is a visual-only identifier, not proof of pet ownership.
- Server-side transaction locks on playground row, unique event keys, daily 30-action cap per member and 8-second action cooldown. Accepted action earns 1 **shared effort** only. Owners spend shared effort to expand room and unlock toys; client balances and pet stats are ignored. No paid features or XP import.
- Events are stored in ordered server sequence and delivered via authenticated foreground WebSocket `/v1/social/live`, with origin check, no tokens in URL, explicit subscribe, heartbeat, membership reauthorization and snapshot re-fetch on change. The WSS reverse proxy must support Upgrade.
- HTTP polling/snapshot remains available for manual refresh or reconnect. Existing solo playground remains playable offline and is not merged with online social data.
- Room UI in Friends tab for room creation, invitations, members, toy actions, upgrades and visit requests. These controls are **beta** and require physical QA; full multi-creature art synchronization and ownership proof are not yet certified.

## Database migration — MANUAL only, after backup

The existing PostgreSQL volume **does not rerun** `/docker-entrypoint-initdb.d/` when restarting. To install D schema, use the additive `server/sql/004_shared_playground.sql` only after taking a verified local `pg_dump -Fc` backup and ensuring the `trialum_app` role exists (see B private QA guide). **Never use `docker compose down -v`.**

```bash
cd /opt/trialum/server
umask 077
mkdir -p /root/trialum-db-backups
docker compose exec -T trialum-db pg_dump -U trialum -d trialum_social -Fc > /root/trialum-db-backups/pre-D.dump
test -s /root/trialum-db-backups/pre-D.dump
docker compose exec -T trialum-db psql -X -v ON_ERROR_STOP=1 -U trialum -d trialum_social < sql/004_shared_playground.sql
docker compose exec -T trialum-db psql -U trialum -d trialum_social -tAc "SELECT to_regclass('public.playground_events')"
```

Expected: `playground_events`. Copy updated server files before rebuilding. Keep `TRIALUM_SOCIAL_ENABLED=false` until private two-phone acceptance. The migration is additive but **the SQL file contains GRANT** and must be applied as the DB administrator; do not paste credentials into chats.
