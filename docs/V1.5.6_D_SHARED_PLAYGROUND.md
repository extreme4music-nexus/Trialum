# TRIALUM 1.5.6-D — shared playground, consent visits, authoritative realtime

**Status:** private source beta. Source implementation and automated tests are separate from real Android/network acceptance. No production Play Store release. Shared service is **DISABLED BY DEFAULT** even if friends B is enabled.

## Player experience
1. Open **Повеќе → 🌳 Заедничка игротека**. Creating a hosted group requires an already unlocked local solo playground (pet evolution >=15, lab >=4). This is a **client-side UX gate only** until a future server-verified progression layer exists; never treat client claims as ranked progression.
2. An opted-in pseudonymous player can create at most 2 hosted groups with a title (1–48 characters), each up to 6 members. Groups initially contain sandbox and seesaw.
3. Only the owner invites an existing, nonblocked friend, who receives a private pending invitation valid 24 hours and MUST explicitly accept. Joining a friend's space does **not** require having unlocked one's own solo playground; personal unlocks are unchanged.
4. Members contribute by playing with server-listed toys. Each server-validated event earns **exactly one shared effort point** (6 per member per UTC day, 8-second cooldown). The server ignores client XP, currencies, pet levels and client-supplied reward amounts. Only a validated cosmetic pet snapshot is shared (name, type, color, eyes, shape, growth, seed).
5. Group owner can use earned shared points to unlock slide (8), pool (10), obstacle course (12) or trampoline (14), subject to available slots. Space expands from tier1 to tier5 for 10/15/20/25 shared points. Members cannot spend group points, but any member can contribute. All toys and spaces are free-earnable; there are no paid-only items.
6. Friend-to-friend pet visits: home or a shared group that both users can access. Sender proposes a temporary cosmetic visit; receiver accepts, declines or returns it. Pending 15 minutes, accepted at most 2 hours; no XP or currency paid for arrival. Home visitor is displayed temporarily and is never inserted into the receiver's local saved pets.
7. WebSockets over WSS signal **only** that group/member state changed. The client fetches a fresh, authorized PostgreSQL snapshot. The canvas animates multiple recent pets/visitors locally, not as video streaming. Eight-second fallback polling is used while the shared screen is foregrounded. Client opt-in is mandatory; no social network call on startup for an unregistered player.

## Privacy / permissions
- Server stores pseudonymous installation ID/nickname, group membership, bounded pet cosmetic state and audited effort events only. **No email, phone, contacts, advertising ID, raw location, data brokers, external ads, payment credentials, or long-form public chat**.
- Bearer credential is SHA-256-only in PostgreSQL and Android Keystore-encrypted in native no-backup storage. A WebSocket authenticates in its first WSS frame; credentials never appear in the URL or scene data.
- Room reads require the player's active membership AND a surviving friendship with the owner. Invite acceptance is explicit. Blocking/removing a friend revokes access. Owners can remove members; members can leave. Owner account deletion deletes owned rooms and children. Group departure removes member-specific cosmetic events/activity history; spent and earned shared *aggregate* balance remains with the group.
- Retention: visits 7 days, invitation expiry and disposal, shared activity and events 30 days, spending audit 90 days. No external reporting/telemetry.
- The server app DB role is least-privilege for group tables, while `short_messages` and `push_registrations` stay inaccessible until phase E. Database and Webmin must remain private. No public Funnel until a separate security and safety audit.
- On a user entering shared space: only pseudonymous names and activity cosmetics of consenting group members/visitors appear. Do not show exact age, private location or contact details.

## Security, economy and scaling caveats
- Client can supply its pet's *appearance*, NOT proven possession, XP or level. Therefore this phase **does not claim anti-cheat certification of pet identity or progression**. The only spendable shared points are earned under server-side rate limits and idempotent transaction keys, with PostgreSQL row-level locks and server-set costs. Do not integrate personal/paid currency into this API until cryptographic receipt and game-state verification exists.
- WebSocket fanout is **single-node**, authenticated and capped (3 sockets per identity, 150 global beta connections, bounded payload, origin and room authorization). Cloud scale-out will require a shared broker (e.g. Redis pub/sub) and edge rate limits; polling works on the private single host.
- Social registration/room creation are still pseudonymous with limited in-process rate buckets, not production anti-spam controls. Phase F audit must address fake-identity flooding, reporting, account recovery and child safety before public hosting.
- Social and shared service are independent feature flags, so disabled mode cannot contact or mutate shared rooms.
- No account log-in screen is required for solo play; do not store social credentials in local world backups.

## API surface
- `GET /v1/shared/status`, `GET/POST /v1/shared/rooms`
- `GET /v1/shared/rooms/:id/snapshot`; `POST /v1/shared/rooms/:id/invite`, `activity`, `upgrade`; `DELETE /v1/shared/rooms/:id`, `members/:id`
- `GET /v1/shared/invitations`, `POST /v1/shared/invitations/:id/accept|decline`
- `GET/POST /v1/shared/visits`, `POST /v1/shared/visits/:id/accept|decline|return`
- `WSS /v1/social/live` (first frame auth; then authorized subscribe; room-change hints only)
