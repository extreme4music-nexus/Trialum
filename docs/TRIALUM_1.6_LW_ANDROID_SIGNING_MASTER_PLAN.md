# TRIALUM 1.6-LW — Official Android Signing Master Plan

**Decision date:** 2026-11-10. **Owner priority:** mandatory security/infrastructure phase **before any further implementation of 1.6-LW-A sessions or LW-B**.

**Status (2026-11-11): S1 inventory/backup PASS; S2–S3 GitHub signing infrastructure PASS, both owner-controlled Release and separate SignQA APK candidates cryptographically signed and verified on GitHub.** Run [42924886058](https://github.com/extreme4music-nexus/Trialum/actions/runs/42924886058) latest attempt succeeded, see [signature evidence and owner runbook](TRIALUM_1.6_LW_GITHUB_SIGNING_SETUP.md). **Real-device SignQA installation/restore, old-app data migration and subsequent owner gate remain PENDING.** No APK has been installed on the owner's device or publicly released as a consequence. This is **not** a Google Play release.

## S0. Frozen known-good baseline / safety invariant

- Current source: `main`, Trialum `1.6-LW-dev.1`, `versionCode=24`, SDK 36, verified previously in dual-APK workflow [42903151143](https://github.com/extreme4music-nexus/Trialum/actions/runs/42903151143). This is our **source baseline**, not proof that an installed APK uses a specific certificate.
- Main package: `com.trialum.ziivaiskra`; existing isolated 1.6 tester: `com.trialum.ziivaiskra.lw16`; historic QA: `com.trialum.ziivaiskra.lwa`.
- Android APKs are already technically signed by debug certificate(s). The current GitHub workflow can optionally restore `TRIALUM_PGS_DEBUG_KEYSTORE_B64`; otherwise each fresh GitHub runner may create a different debug signing key. **Do not assume** any installed app matches the runner or a new release signing key.
- LW-A recovery's `TrialumBackupVault.kt`, protected restore, unique SHA-256 verified JSON backups, pinned rescue before restore/reset, model/XP/achievements/history preservation, presence logic, server identity, and all existing save formats **MUST remain unchanged**.
- **Never** uninstall, clear storage, overwrite a valuable backup, run a destructive Restore on real owner data, change a package name of the existing main app, or push a production/server/Play update to complete signing. Existing `.lwa` and `.lw16` installation data are independent; app-private vault and Android Keystore social credentials are **not portable** simply by copying world JSON.

## S1. Signing-certificate inventory first — BLOCKING

1. Preserve exact last-known-good APK artifacts, hashes and GitHub run/commit; keep backups in safe storage outside the Android sandbox.
2. From the **actual installed** `com.trialum.ziivaiskra`, historic `.lwa` and current `.lw16` packages, where installed, determine each package name, `versionCode` and APK signer SHA-256 fingerprint. Use an exported installed APK (e.g. `adb shell pm path <package>`, `adb pull ...`) plus Android SDK `apksigner verify --print-certs <apk>`; compare against actual original APK archives from the owner. Record public certificate SHA-256 values only, not secrets.
3. Inspect GitHub debug signing policy: whether the optional stable `TRIALUM_PGS_DEBUG_KEYSTORE_B64` has been configured (its value need never be displayed). Independently confirm any matching SHA-256 fingerprint from the CI APK. Never assume a CI green check proves update compatibility.
4. **Decision gate:** If any newly signed APK has the same package name but a different signer, Android will refuse the in-place update. Such a candidate is **not installed**; preserve existing data and use the independent QA package/verified external world restore. A new signing key cannot magically update old debug-signed installations.
5. Record exported world backup file size, nonzero JSON validity, pet/habitat counts, day, XP, achievements and journal checksums before a QA migration. Do not expose personal game/social state in logs.

**S1 exit:** documented package-ID ↔ signer-SHA256 matrix, safe installation strategy and offline copy of all user-critical backup files. If any device cannot be inspected, explicitly label the corresponding upgrade path **UNVERIFIED / BLOCKED**.

## S2. Permanent keys and owner custody — BLOCKING

Recommend **two distinct, long-lived signing identities**, both generated by the project owner on a trusted local computer, not in a public workflow, chat transcript or repository:

- **Production/app identity (`trialum-release`)**: a dedicated long-lived `.jks` for future signed candidate APKs carrying the normal package `com.trialum.ziivaiskra`. Do not repurpose an ephemeral Android debug key or the Google Play Games debug keystore. RSA 3072/4096 with SHA-256 and at least 25–30-year certificate validity; unique alias, strong store/key passwords. Record its *public* certificate SHA-256 fingerprint in the signing manifest.
- **Independent QA identity (`trialum-qa`)**: a separate signing key for signed test APKs. To avoid breaking the installed `com.trialum.ziivaiskra.lw16` debug tester, introduce a **new dedicated QA package** (proposed `com.trialum.ziivaiskra.signqa`), unless the owner independently proves that a different existing QA package can safely receive a same-certificate update. Do not force this new identity onto `.lwa` or `.lw16`.

Keep **at least two securely protected offline backups** of each keystore, physically/logically separated (e.g. encrypted offline drive plus separately protected backup). Store passwords in a password manager, independently of the keystore files. Test recovery on a disposable test setup. Record fingerprint, alias, creation date, validity and versioned custody procedure; never commit or transmit private key/password contents in chat. The GitHub copy is a controlled operational copy, not the *only* master.

**Play compatibility:** Google Play App Signing later needs an explicit decision on app-signing vs upload keys and matching externally distributed APK identity. Keep the release key for a future Play enrollment strategy; do not assume Play will use the same signing identity automatically.

## S3. Protected GitHub secret distribution

Use a dedicated **GitHub Actions Environment**, e.g. `trialum-signing`, protected with branch restrictions and approval where supported, and minimum required workflow token permissions. Only a trusted owner-initiated `workflow_dispatch` from protected `main` or a protected signing tag can enter the signing job. Never expose signing secrets to untrusted `pull_request`/`pull_request_target` source, arbitrary forks, third-party PR code, user-supplied scripts or uncontrolled dependency updates.

Proposed environment secrets (names only; values added privately by the owner in GitHub Settings):
- `TRIALUM_RELEASE_KEYSTORE_B64`, `TRIALUM_RELEASE_STORE_PASSWORD`, `TRIALUM_RELEASE_KEY_PASSWORD`, `TRIALUM_RELEASE_KEY_ALIAS`.
- Separately, QA: `TRIALUM_QA_KEYSTORE_B64`, `TRIALUM_QA_STORE_PASSWORD`, `TRIALUM_QA_KEY_PASSWORD`, `TRIALUM_QA_KEY_ALIAS`.

Base64 is **transport encoding, not encryption**. Decode into a restrictive ephemeral file under the Actions runner temporary directory and delete it after use; never upload raw keystores, secret-containing Gradle properties or stdout logs. Secrets must be required for the signing job: missing/empty/invalid secret means **FAIL CLOSED** (not a fallback to debug-signing and misleadingly renamed APK).

## S4. CI design (development branch, PR review, owner-controlled signing)

1. **Preserve** current normal `assembleDebug` and independent `assembleLw16` as regression artifacts. Do not rename/debug-sign those and pretend they are release-signed.
2. Add a dedicated, *manual*, restricted signing workflow using Gradle `signingConfigs` for the controlled production-like `release` or `candidate` variant, plus an isolated signed QA build type with its own application ID and QA signing config. Non-debuggable candidate by default. Do not modify normal `applicationId`, save schema or production server endpoints.
3. The signing workflow **depends on full JS, Android SDK36, presence/backup and social-server gates on the exact source SHA**. It signs *only* the reviewed commit, not whatever `main` becomes while building. Use trusted maintained actions pinned to approved revisions (ideally immutable commit SHAs).
4. Verify generated APKs with `apksigner verify --verbose --print-certs`, not only by checking that a file exists. Enforce expected fixed package ID, signed variant identity, non-debuggable manifest for production candidate, expected monotonically increasing versionCode, public signer SHA-256 allowlist, signature scheme compatibility, and complete bundled world assets/backup vault. Record APK SHA-256 and source commit in a public, **non-secret** provenance manifest. Any failure blocks uploading the signed artifact.
5. Upload signed candidate and signed isolated QA artifacts to a restricted GitHub Actions run, with separate explicit names such as `Trialum-1.6-LW-Signed-Candidate` and `Trialum-1.6-LW-Signed-QA`. These are **internal testing artifacts** until owner authorization. Never auto-publish to Releases, Play, public download pages or social networks.
6. Keep 1.5.6-F and older LW-A debug artifact identities as immutable history. Do not retroactively re-sign or repackage historical APKs.

## S5. Physical QA — REQUIRED before permitting real updates

On a disposable/test installation, verify these cases:

- Same package + same signer + higher versionCode installs as an update and preserves game day, pets, habitats, levels, XP, credits, achievements, logs, theme, optional model consent and legitimate social session where applicable.
- Same package + mismatched signer **correctly refuses** update; do not remove the installed original to make the test pass.
- Signed `.signqa` can coexist with the original, `.lwa` and `.lw16` packages, with independently isolated local storage, Android Keystore and invite URI scheme.
- Export world JSON **twice** → two distinct, nonempty SHA-256-verified files; restore from **copied** JSON into independent QA package; test bad/0-byte/corrupt files, canceled restore, failed disk write and mandatory pinned rescue blocking destructive reset. Original source backup remains intact. Validate old save round-trip and presence migration. Private rescue data and social credentials must not be falsely claimed transferable by JSON.
- Offline/online and app restart with session/presence code must not duplicate pets or corrupt save state. Existing missing LW-A session lifecycle is **not magically fixed** by signing; its implementation belongs after signing acceptance.
- Verify SHA-256 fingerprint of the **installed** APK after signing and compare to manifest; document screenshots, checksums and device/Android version. Human owner approval is separate from CI PASS.

**S5 exit:** exact SHA CI PASS, signing certificate fingerprint PASS, verified private backup/restore pass on test data, safe update/coexistence on test device, owner's explicit sign-off. No new main-app update until *its actual installed signer* is proven compatible.

## S6. Rollback / compromise

- If signing CI fails: do not publish artifacts and do not touch installed apps; preserve last-known-good dual-APK CI.
- If QA fails: freeze candidate, keep current data, investigate source/Gradle/signature discrepancy in a new branch and rerun on the same baseline.
- If a keystore is lost/compromised: block new builds; do not silently create a replacement under the same package ID and claim it updates old installations. Record an owner-approved identity-rotation or distribution-transition plan with Android/Play constraints.
- NEVER include keys, passwords, world exports, credentials or production `.env` in PRs, screenshots, build artifacts or test logs.

## Release naming and gates

**Signing is a development infrastructure gate, not a Google Play release.** Avoid changing `1.6-LW-dev.1` into `1.6-LW-final` simply because it is signed. A signed APK is an authenticity mechanism, not proof of privacy, age suitability, Google verification or publication readiness.

**S1 → S2 → S3 → S4 → S5 → owner sign-off (S6 housekeeping) → resume 1.6-LW-A sessions.** No LW-B before LW-A is separately accepted. Google Developer Verification for broader non-Play distribution is a **separate** topic, with rollout begun in selected countries on 2026-09-30 and further expansion in 2027; GitHub signing alone does not constitute verification.
